# BLUEDA 테스트 진행 방법

같은 테스트를 계속 돌리면 언젠가는 새 버그를 찾지 못합니다. 살충제 패러독스입니다.
BLUEDA에서도 실제로 겪었습니다. v0.5.3 회귀 테스트에서 고정 테스트 350개는 모두 통과했지만, 무작위 검증을 처음 돌리자 버그 3건이 나왔습니다.
v0.5.4에서는 돌연변이 테스트를 처음 돌렸습니다. 분석 범위 모듈의 돌연변이 중 44%를 기존 테스트가 잡지 못했습니다. 빈틈을 메우다가 날짜 필터 코드 로그 버그도 찾았습니다.
"코드 로그가 실행되는가"만 확인하는 테스트는 있었지만, "같은 결과가 나오는가"를 확인하는 테스트는 없었기 때문입니다.
같은 날 속성 기반 테스트도 저장소에서 처음 돌린 때는 통과했지만, 다른 입력으로 다시 돌리자 시간대가 섞인 값에서 멈추는 버그를 찾았습니다(`blueda/safedate.py`로 수정).
그래서 BLUEDA는 테스트를 고정해 두지 않고, 입력과 관점을 계속 바꾸는 방식으로 진행합니다.

## 1. 테스트 층

| 층 | 파일·도구 | 입력이 바뀌는 방식 | 찾는 것 |
|---|---|---|---|
| 고정 테스트 | tests/test_*.py | 바뀌지 않음 (예전 버그가 다시 생기는지 확인) | 알려진 버그 재발 |
| 무작위 검증 | tests/test_fuzz.py | 실행마다 시드가 바뀜 | 사람이 생각 못 한 데이터·필터 조합 |
| 속성 기반 테스트 | tests/test_properties.py (Hypothesis) | 경계값·이상한 글자를 자동으로 만들고 실패 입력을 최소로 줄임 | 어떤 입력에도 지켜져야 할 규칙 위반 |
| 돌연변이 테스트 | mutmut | 코드를 일부러 망가뜨림 | 테스트가 놓치는 곳 (테스트의 품질) |
| 골든 마스터·스크린샷 비교 | 저장소 밖 도구 (실습 데이터 사용) | 버전끼리 비교 | 의도하지 않은 결과·화면 변화 |
| 탐색적 테스트 | 차터 (5절) | 단계마다 새 주제 | 문서·테스트에 없는 사용 흐름의 문제 |
| 윈도우 수동 확인 | 개인 PC | - | 글꼴·배율·끌어다 놓기 |

## 2. 언제 무엇을 돌리나

| 시점 | 할 일 | 명령 |
|---|---|---|
| 코드를 고칠 때마다 | 전체 자동 테스트 (무작위 25회, 속성 예시 60개 포함) | `pytest -q` |
| 단계 마무리 | 무작위 400회 이상, 속성 예시 500개, 실습 데이터 비교 | `BLUEDA_FUZZ_TRIALS=400 HYPOTHESIS_PROFILE=thorough BLUEDA_TEST_DATA=<경로> pytest -q` |
| 단계 마무리 | 돌연변이 테스트 (모듈 1~2개씩 돌아가며) | 4절 |
| 단계 마무리 | 탐색적 테스트 차터 1개 이상 | 5절 |
| 버전 출시 전 | 골든 마스터·스크린샷 비교, 120만 행 성능 비교 | 이전 버전과 비교 |

무작위 검증이 실패하면 메시지에 `seed=` 값이 나옵니다. `BLUEDA_FUZZ_SEED=<값> pytest tests/test_fuzz.py`로 같은 데이터를 다시 만들 수 있습니다.

## 3. 테스트를 바꿔 가는 규칙

1. **버그를 고치면 테스트부터 남깁니다.** 고치기 전 코드에서 그 테스트가 실패하는지 확인합니다. 고친 코드에서만 돌려 보면 테스트가 정말 버그를 잡는지 알 수 없습니다.
2. **무작위 검증에서 나온 시드는 고정 목록으로 옮깁니다.** test_fuzz.py의 `FOUND_SEEDS`에 넣고, 짧은 단위 테스트도 따로 만듭니다.
3. **테스트의 판정 기준을 약하게 두지 않습니다.** "오류 없이 실행된다"만 보는 테스트는 결과가 틀려도 통과합니다. 가능하면 "직접 계산한 값과 같다", "코드 로그를 실행하면 같은 결과가 나온다"까지 확인합니다.
4. **새로운 모양의 데이터를 만나면 생성기에 넣습니다.** 실습 파일이나 실제 업무 데이터에서 처음 본 모양(열 이름 형식, 날짜 형식, 결측 표기, 아주 긴 꼬리 등)은 test_fuzz.py의 `make_data`나 test_properties.py의 `frames`에 추가합니다. 생성기를 바꾸면 같은 시드가 다른 데이터를 만듭니다. 그때는 `FOUND_SEEDS`를 예전 코드로 다시 찾아 갱신합니다.
5. **단계마다 테스트 목록을 검토합니다** (6절 체크리스트).
6. **오래 실패하지 않은 테스트는 지우지 않습니다.** 대신 입력을 넓힐 수 있는지 봅니다. 예를 들어 같은 고정 데이터만 쓰는 테스트에 무작위 입력이나 속성 테스트를 덧붙입니다.
7. **새 기능은 테스트 설계 기법을 골라 적용합니다.** 동등 분할, 경계값 분석, 상태 전이(작업 중 파일 열기·창 닫기), 오류 추측(빈 범위, 모두 결측, 1행)을 씁니다. 어떤 기법을 썼는지 커밋 메시지나 테스트 설명에 남깁니다.

## 4. 돌연변이 테스트

코드를 조금씩 망가뜨린 "돌연변이"를 만들고 테스트를 돌립니다. 예를 들면 `<=`를 `<`로, `and`를 `or`로 바꿉니다.
테스트가 실패하면 그 돌연변이를 잡은 것입니다. 모두 통과하면 살아남은 것이고, 그 줄은 테스트가 제대로 확인하지 않는다는 뜻입니다.

- 윈도우에서는 바로 실행되지 않습니다. mutmut 3는 fork가 필요해서 WSL 안에서 돌려야 합니다.
- 설정은 pyproject.toml의 `[tool.mutmut]`에 있습니다. `paths_to_mutate`를 바꿔 가며 모듈 1~2개씩 측정합니다.
- 오래 걸리는 화면 테스트는 빼고 엔진 테스트만 씁니다 (scope.py 기준 10~25분).
- **무작위 입력은 고정하고 돌립니다.** 무작위 테스트가 새 버그를 찾아 실패하면, 그 실패가 돌연변이 때문인지 알 수 없습니다. 그러면 돌연변이를 모두 "잡았다"고 잘못 셉니다. v0.5.4 첫 재측정에서 228개를 모두 잡은 것으로 나왔지만, 실제로는 속성 테스트가 찾은 새 버그 때문에 생긴 착시였습니다.
- **테스트 이름에 한글이 있으면** pytest가 `\uXXXX`로 바꾼 이름을 mutmut에 넘기고, 그 이름으로는 테스트를 찾지 못해 모두 "잡음"이 됩니다. pyproject.toml의 `[tool.pytest.ini_options]`에서 이름을 바꾸지 않게 해 두었습니다. 지우면 안 됩니다.
- 측정을 시작하기 전에 테스트 전체가 통과하는지 먼저 확인합니다. 결과가 너무 좋게 나오면 잡을 수 없는 돌연변이 하나를 직접 돌려 봅니다 (`MUTANT_UNDER_TEST=<이름> pytest ...`, `mutants/` 폴더 안에서).

```bash
pip install mutmut          # WSL 안에서
HYPOTHESIS_PROFILE=fixed BLUEDA_FUZZ_SEED=0 BLUEDA_FUZZ_TRIALS=5 mutmut run   # 결과는 mutants/ 폴더 (저장소에 올리지 않음)
mutmut results              # 살아남은 돌연변이 목록
mutmut show <이름>           # 어떤 줄을 어떻게 바꿨는지
```

살아남은 돌연변이는 둘 중 하나로 처리합니다.
- 결과가 달라지는데 테스트가 못 잡은 경우: 테스트를 추가합니다.
- 결과가 같은 경우(동등 돌연변이. 예: 기본값이 같은 인자, 안내 문장의 띄어쓰기): 표에 이유를 적고 넘어갑니다.

| 측정일 | 모듈 | 돌연변이 | 잡음 | 살아남음 | 비고 |
|---|---|---|---|---|---|
| 2026-11-24 | scope.py (보강 전) | 221 | 124 (56%) | 97 | 첫 측정. 아래 한글 이름 문제가 섞였을 수 있어 실제 비율은 더 낮을 수 있음 |
| 2026-11-24 | scope.py (보강 후) | 223 | 213 (95.5%) | 10 | test_scope_rules.py 추가. 남은 10개는 아래 표 |

scope.py에서 살아남은 10개 (모두 테스트로 잡을 수 없거나 환경에 따라 다름):

| 돌연변이 | 판단 |
|---|---|
| `dtype=bool` 삭제·None (4개) | 동등. 이미 True/False 배열 |
| `m &= s >= lo` → `m = s >= lo` | 동등. 앞에서 m이 모두 True |
| `fillna(False)` → None·True (2개) | 지금은 동등. 필터 마스크에 결측이 생기지 않음 (방어 코드) |
| 날짜형 판단에 열 대신 None | 결과 동등. 날짜형 열에 Timestamp를 직접 넣는 경우만 코드 로그 글자가 달라짐 |
| `engine="python"` 삭제·None (2개) | 환경에 따라 다름. numexpr가 설치된 PC에서는 기본 엔진이 바뀌어 일부 직접 입력 조건이 실패할 수 있음. 이 환경에는 numexpr가 없어 확인 불가 |

## 5. 탐색적 테스트 차터

정해진 순서 없이 시간을 정해 놓고 사용해 보며 문제를 찾습니다. 차터는 "무엇을, 무엇으로, 무엇을 알아내려고"로 씁니다.

```
차터: <탐색 대상>을 <사용할 데이터·도구>로 탐색해 <알아낼 정보>를 찾는다
시간: 30~60분
기록: 해 본 것, 발견한 것(버그·불편·질문), 다음 차터 후보
```

다음 차터 후보입니다. 한 번 한 차터는 결과와 함께 아래 기록 표로 옮깁니다.

1. 실제 업무 엑셀(병합 셀, 머리글 2줄, 맨 아래 합계 행)을 열어 보고 전처리 점검이 무엇을 알려 주는지
2. 120만 행 파일로 작업 도중 취소, 다른 파일 열기, 필터 바꾸기를 섞어 멈춤이나 잘못된 결과가 있는지
3. 히스토리 복원을 다른 파일·날짜 변환 뒤에 했을 때 조건이 맞게 돌아오는지
4. 윈도우 화면 배율 150%와 다크 모드에서 모든 창의 글자가 잘리거나 겹치는지 (개인 PC)
5. 처음 쓰는 사람의 입장에서 사용방법 문서만 보고 실습 과제 하나를 끝낼 수 있는지

## 6. 단계 마무리 체크리스트

- [ ] 전체 테스트 통과 (실습 데이터 포함)
- [ ] 무작위 400회 이상, 속성 예시 500개 통과
- [ ] 커버리지가 가장 낮은 모듈 3개 확인. 그중 하나에 테스트 보강 (`pytest --cov=blueda --cov-report=term-missing`)
- [ ] 돌연변이 테스트를 지난번과 다른 모듈로 측정. 살아남은 돌연변이 처리
- [ ] 이번 단계에서 새로 본 데이터 모양을 생성기에 추가
- [ ] 탐색적 테스트 차터 1개 이상 실행하고 기록
- [ ] 고친 버그마다 고치기 전 코드에서 실패하는 테스트가 있는지 확인
- [ ] 결과를 CHANGELOG와 개발계획 문서(6-1-x)에 기록

## 8. 알고 있는 빈틈 (다음에 할 일)

- 골든 마스터 시나리오 149개에 "글자 날짜 + 기간 필터"가 없고, 범위 코드 로그도 비교하지 않습니다. 그래서 v0.5.4의 날짜 코드 로그 버그를 골든 비교로는 잡지 못했습니다. 시나리오를 추가해야 합니다.
- 골든 마스터·스크린샷 비교 도구는 실습 데이터를 쓰기 때문에 지금은 저장소 밖에 있습니다. 실습 데이터 없이 도는 부분만 따로 떼어 저장소에 넣는 것이 다음 후보입니다.
- 분석 결과 코드 로그(분산분석, 회귀 등)는 아직 "실행된다"까지만 확인합니다. 피벗·교차표처럼 "같은 값이 나온다"로 올려야 합니다.
- 시간대가 섞인 날짜는 툴에서는 UTC로 맞춰 처리하지만, 기간 필터·월별 피벗의 코드 로그는 `pd.to_datetime(..., errors='coerce')` 그대로입니다. 이런 데이터에서는 Colab에서 코드 로그가 오류를 낼 수 있습니다.
